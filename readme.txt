================================================================================
PMake 1.3.2 - Руководство пользователя
================================================================================

PMake - кроссплатформенная система сборки с собственным языком манифестов
build.pmake и поддержкой Ninja-файлов build.ninja.

Это руководство описывает практическую работу с PMake: установку, запуск,
синтаксис манифеста, правила сборки, зависимости, функции, кэш и совместимость
с CMake/Ninja.

--------------------------------------------------------------------------------
1. Быстрый старт
--------------------------------------------------------------------------------

Для запуска PMake нужен исполняемый файл pmake:

    pmake --version
    pmake --help

Если рядом с текущей директорией находится build.pmake, PMake использует его.
Если такого файла нет, PMake ищет build.ninja. Другой манифест задаётся явно:

    pmake -f путь/к/build.pmake

Создайте файл build.pmake:

    pmake_required_version = 1.0

    if os == "windows" {
        cxx = "g++"
        exe_ext = ".exe"
    } else {
        cxx = "g++"
        exe_ext = ""
    }

    flags = "-std=c++20 -O2"

    rule compile {
        command     = "${cxx} ${flags} -c ${in} -o ${out} -MMD -MF ${out}.d"
        description = "Компиляция ${in}"
        depfile     = "${out}.d"
        deps        = "gcc"
    }

    rule link {
        command     = "${cxx} ${flags} ${in} -o ${out}"
        description = "Компоновка ${out}"
    }

    build "build/main.o" : compile "src/main.cpp"
    build "build/app${exe_ext}" : link "build/main.o"
    alias all : "build/app${exe_ext}"

Запустите сборку из директории проекта:

    pmake

PMake выберет alias all, если он объявлен. Можно также указать цель напрямую:

    pmake "build/app.exe"

Каталоги для выходных файлов PMake создаёт автоматически.
Для примера нужны компилятор g++ и файл src/main.cpp.

--------------------------------------------------------------------------------
2. Сборка PMake из исходного кода
--------------------------------------------------------------------------------

Рекомендуемый способ - CMake и Ninja. Нужны CMake 3.25 или новее, компилятор
с поддержкой C++23 и Ninja:

    cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release
    cmake --build build

Ожидаемое расположение программы:

    Windows:    build/pmake.exe
    Linux/macOS: build/pmake

После генерации CMake-манифеста PMake может собрать проект через Ninja-файл:

    cd build
    pmake

Проверка тестов из корня репозитория (после сборки вернитесь в корень):

    cd ..
    cd tests-pmake/basic
    python run.py --generate-only

Затем запустите тесты с собранным бинарным файлом:

    Windows:     python run.py --pmake ../../build/pmake.exe
    Linux/macOS: python run.py --pmake ../../build/pmake

--------------------------------------------------------------------------------
3. Командная строка
--------------------------------------------------------------------------------

Общий формат:

    pmake [параметры] [цели...]
    pmake -t ИНСТРУМЕНТ [цель]

Основные параметры:

    -f FILE, --file FILE       Путь к манифесту.
                               По умолчанию build.pmake, затем build.ninja.
    -j N, --jobs N             Максимальное число параллельных задач.
    -n, --dry-run              Показать планируемые задачи, не запускать их.
    -v, --verbose              Подробный вывод, включая команду и workdir.
    -q, --quiet                Скрыть обычный вывод, оставить ошибки.
    --config NAME              Выбрать блок config (по умолчанию release).
    --platform NAME            Выбрать блок platform.
    --no-color                 Отключить цветной вывод.
    -V, --version              Показать версию.
    -h, --help                 Показать справку.

Параметр `-f` выбирает манифест, но не меняет текущую директорию. Для
CMake-generated Ninja-файла запускайте PMake из build-директории, чтобы
относительные пути в манифесте разрешались правильно.

Инструменты, выбираемые только через -t:

    pmake -t list
    pmake -t targets
    pmake -t commands
    pmake -t commands app
    pmake -t clean
    pmake -t clean app

Названия целей не зарезервированы. Например, `pmake clean` собирает цель
с именем clean, если она есть в манифесте. Команда очистки - `pmake -t clean`;
с указанием цели удаляются только её выходы, входы остаются нетронутыми.
Аналогично, `pmake help` означает цель help, а не встроенную справку.

Коды завершения:

    0    Команда завершилась успешно.
    1    Ошибка манифеста, сборки или поиска цели.
    130  Сборка прервана пользователем (Ctrl+C).

--------------------------------------------------------------------------------
4. Структура build.pmake
--------------------------------------------------------------------------------

Обычно манифест содержит:

  1. Объявление минимальной версии синтаксиса.
  2. Переменные и выбор настроек по ОС/конфигурации.
  3. Правила (rule) - шаблоны команд.
  4. Сборки (build) - цели, правила и зависимости.
  5. Alias all - привычная общая цель проекта.

    pmake_required_version = 1.0

    cxx = "g++"
    flags = "-O2"

    rule compile {
        command = "${cxx} ${flags} -c ${in} -o ${out}"
    }

    build "main.o" : compile "main.cpp"
    alias all : "main.o"

Манифест выполняется при загрузке: PMake вычисляет переменные, условия и
списки целей, после чего строит граф зависимостей. Команды правил запускаются
только для целей, которые требуется пересобрать.

Комментарии:

    // Однострочный комментарий

    /*
       Многострочный
       комментарий
    */

Символ `#` не является началом комментария и приведёт к ошибке синтаксиса.

--------------------------------------------------------------------------------
5. Переменные, строки и списки
--------------------------------------------------------------------------------

Присваивание:

    project = "Demo"
    object_ext = ".o"

Подстановка в строку:

    output = "build/${project}"

Оператор += добавляет значение через пробел:

    flags = "-O2"
    flags += "-Wall"
    // flags теперь содержит "-O2 -Wall"

Поддерживаются строки, числа, логические значения и списковые выражения:

    count = 4
    enabled = true

Список можно передать циклу напрямую:

    foreach source in ["main.cpp", "util.cpp"] {
        build "build/${source}.o" : compile "${source}"
    }

Элементы списка разделяются запятыми. Сохранение списка в переменную пока не
поддерживается: такое присваивание даёт пустое значение.

Строки заключаются в двойные кавычки. Поддерживаются escape-последовательности
`\"`, `\\`, `\n` и `\r`. Неизвестные сочетания с обратной косой чертой
сохраняются как написаны, что удобно для Windows-путей.

Области видимости:

  - Переменные вне блоков доступны всему манифесту.
  - Локальные значения можно задать внутри блока build.
  - Параметры функций и переменные циклов доступны в своих блоках.
  - Блоки config и platform добавляют выбранные значения к настройкам проекта.

Пример локальных переменных сборки:

    build "debug.o" : compile "main.cpp" {
        flags = "-g -O0"
    }

--------------------------------------------------------------------------------
6. Правила (rule)
--------------------------------------------------------------------------------

Правило задаёт команду и необязательные свойства:

    rule compile {
        command     = "${cxx} ${flags} -c ${in} -o ${out}"
        description = "Компиляция ${in}"
        depfile     = "${out}.d"
        deps        = "gcc"
        restat      = true
        generator   = false
        rspfile     = "${out}.rsp"
        rspfile_content = "${in_newline}"
    }

Поля правила:

    command
        Команда компилятора или другой программы.

    description
        Краткое описание задачи в выводе сборки.

    depfile
        Путь к .d-файлу с зависимостями, например заголовками C/C++.

    deps
        Формат зависимостей. Для Make/GCC-совместимых .d-файлов используйте
        "gcc"; для трассировки заголовков MSVC — "msvc" вместе с /showIncludes.

    restat
        После выполнения сравнивает выходные файлы. Если они не изменились,
        зависимые задачи можно пропустить.

    generator
        Помечает правило генерации манифеста или других генерируемых файлов.
        Используется, в частности, для автоматической регенерации CMake/Ninja.

    rspfile, rspfile_content
        Путь и содержимое response-файла. PMake записывает его перед запуском
        команды и удаляет после выполнения.

    pool
        В PMake DSL значение "console" назначает задаче последовательный пул.
        Ninja-манифесты также могут описывать пулы с ограниченной глубиной.

Специальные переменные:

    ${in}          Входы задачи, объединённые в строку с экранированием путей.
    ${out}         Выходы задачи, объединённые в строку с экранированием путей.
    ${in_newline}  Входы, разделённые переводами строк.
    ${rspfile}     Путь к response-файлу, если он задан в правиле.

Переменные доступны в command, description и rspfile_content. Для multi-output
правила `${out}` содержит все объявленные выходы.

Важно: PMake запускает программу напрямую, не через shell. Поэтому `>`,
`|`, `&&` и shell-переменные сами по себе не обрабатываются. Чтобы использовать
редирект или конвейер, явно запускайте оболочку, например `cmd /c` в Windows
или `sh -c` в Linux/macOS. Для компилятора и линкера оболочка не требуется.

--------------------------------------------------------------------------------
7. Цели и зависимости (build)
--------------------------------------------------------------------------------

Базовый синтаксис:

    build "выход" : правило "вход1" "вход2"

Несколько входов разделяются пробелами:

    build "app" : link "main.o" "util.o"

Несколько выходов разделяются запятыми:

    build "a.txt", "b.txt" : generate "input.txt"

Типы зависимостей:

    build "app" : link "main.o" | "config.h" || "stamp"

  - Перед `|` - обычные входы. Изменение входа вызывает пересборку.
  - После `|` - неявные входы. Они также вызывают пересборку, но обычно
    не передаются в `${in}`.
  - После `||` - order-only зависимости. PMake ждёт их завершения, но само
    изменение такой зависимости не является причиной пересборки.

Файл, который задаёт зависимость, может отсутствовать только если манифест
и используемое правило допускают этот сценарий. Обычная сборка ожидает, что
все объявленные выходы будут созданы успешно завершившейся командой.

Alias создаёт phony-цель, объединяющую несколько целей:

    alias all : "app", "tests"

`all` - общепринятое имя основной цели PMake. Можно собирать и отдельные цели:

    pmake app
    pmake app tests

8. Инкрементальная сборка, depfile и кэш
--------------------------------------------------------------------------------

Перед запуском PMake сравнивает выходы и зависимости. Если выход отсутствует,
вход новее или изменился список зависимостей из depfile, соответствующая задача
перезапускается.

Пример для C/C++:

    rule compile {
        command = "${cxx} -c ${in} -o ${out} -MMD -MF ${out}.d"
        depfile = "${out}.d"
        deps = "gcc"
    }

Компилятор записывает заголовки в `${out}.d`; PMake использует их при следующих
сборках. Перед запуском команды старый depfile удаляется; если после успешной
компиляции новый файл отсутствует или некорректен, сборка завершается ошибкой,
а не использует устаревшие зависимости. Пустой корректный depfile допустим.
Указывайте depfile только если команда действительно его создаёт.

Для MSVC-зависимостей depfile не нужен: включите вывод `/showIncludes` в команду
и задайте `deps = "msvc"`. PMake распознаёт трассировку включённых файлов и
использует её для инкрементальной пересборки. Предупреждения компилятора,
записанные в stderr, показываются и при успешной сборке.
В Windows PMake автоматически включает UTF-8 для консольного вывода и
преобразует системные сообщения об ошибках в UTF-8, чтобы кириллица
отображалась корректно.

PMake хранит состояние в `Project-cache.pmake` в текущей рабочей директории.
Кэш содержит сведения о манифестах, целях, командах и зависимостях. Изменения
главного или включённого манифеста, конфигурации и платформы инвалидируют
соответствующие данные кэша. Старый или повреждённый кэш можно удалить:
PMake создаст его заново.

Если команда сборки завершается ошибкой, PMake удаляет её объявленные выходы,
response-файл и depfile, чтобы частичный артефакт не считался актуальным.
При принудительном завершении процесса средствами ОС очистка не гарантируется.

--------------------------------------------------------------------------------
9. Конфигурации и платформы
--------------------------------------------------------------------------------

Блоки config и platform задают значения, которые применяются при загрузке
соответствующей конфигурации:

    config debug {
        cflags = "-g -O0"
    }

    config release {
        cflags = "-O2 -DNDEBUG"
    }

    platform windows {
        exe_ext = ".exe"
    }

    platform linux {
        exe_ext = ""
    }

Выбор:

    pmake --config debug
    pmake --config release --platform windows

По умолчанию используется конфигурация release, а платформа определяется
автоматически: windows, linux или darwin. При изменении конфигурации или
платформы PMake сбрасывает применимость кэша сборки.

Условные выражения также можно использовать непосредственно:

    if os == "windows" {
        exe_ext = ".exe"
    } elseif os == "linux" {
        exe_ext = ""
    } else {
        exe_ext = ""
    }

--------------------------------------------------------------------------------
10. Циклы, условия и функции
--------------------------------------------------------------------------------

Условия поддерживают сравнения, логические операторы и арифметику:

    if config == "debug" && os != "windows" {
        flags = "-g"
    }

Операторы: `==`, `!=`, `<`, `>`, `<=`, `>=`, `&&`, `||`, `!`, `+`, `-`,
`*`, `/`. Условия используют значения переменных и встроенных функций.

Цикл foreach перебирает список:

    foreach source in ["src/main.cpp", "src/util.cpp"] {
        object = replace(source, ".cpp", ".o")
        build "${object}" : compile "${source}"
    }

`break` завершает текущий цикл, `continue` переходит к следующей итерации.
Для циклов с условием используется while:

    index = 0
    while index < 3 {
        index += 1
    }

Выбор одного варианта через switch:

    switch config {
        case "debug" {
            flags = "-g"
        }
        case "release" {
            flags = "-O2"
        }
        default {
            flags = ""
        }
    }

Пользовательские функции принимают параметры и могут возвращать значение:

    function with_warnings(flags) {
        return "${flags} -Wall -Wextra"
    }

    cflags = with_warnings("-O2")

--------------------------------------------------------------------------------
11. Встроенные функции
--------------------------------------------------------------------------------

Пути и списки:

    glob(pattern, directory?)
        Находит файлы по шаблону в указанной директории (по умолчанию -
        директория проекта). Поиск не рекурсивный; результат содержит пути
        найденных файлов.

    basename(path)             Имя файла без родительского каталога.
    filename(path)             Имя файла с расширением.
    dirname(path)               Родительский каталог.
    extension(path)             Расширение без точки.
    absolute_path(path)         Абсолютный путь.
    relative_path(path, base)   Путь относительно base.
    replace_suffix(list, ext)   Заменяет расширения элементов списка.
    join(items..., separator)   Объединяет элементы строкой-разделителем.
    split(text, separator)      Разбивает строку и возвращает список.

Проверки и преобразования:

    exists(path)                Проверяет существование файла.
    file_mtime(path)            Возвращает время изменения файла.
    starts_with(text, prefix)   Проверяет начало строки.
    ends_with(text, suffix)     Проверяет конец строки.
    contains(text, part)        Проверяет наличие подстроки.
    replace(text, old, new)     Заменяет подстроку.
    hash(text)                  Возвращает SHA-1 хэш строки.

Файлы и окружение:

    read_file(path)             Читает текстовый файл.
    write_file(path, content)   Записывает файл и возвращает результат.
    env(name)                   Читает переменную окружения.
    cwd()                       Возвращает текущую директорию.
    dep_inputs(path)            Читает входы из Make/GCC depfile.

Встроенные функции вычисляются при обработке манифеста. Например, `write_file`
создаёт файл во время загрузки манифеста, а не как отдельная задача сборки.
Для отслеживаемых выходов используйте правило build.

--------------------------------------------------------------------------------
12. Подключение манифестов и объявления
--------------------------------------------------------------------------------

Фрагменты манифеста можно подключать:

    include "rules.pmake"
    import "platforms.pmake"

Пути разрешаются относительно файла, в котором находится include/import.
Циклические подключения обнаруживаются и приводят к ошибке.

Дополнительные объявления:

    const BUFFER_SIZE = 4096

    enum BuildMode {
        DEBUG,
        RELEASE
    }

    namespace library {
        internal_flags = "-fvisibility=hidden"
    }

Константы и элементы enum доступны как переменные манифеста. namespace создаёт
область видимости для содержащихся в нём объявлений; это не механизм загрузки
внешнего пакета и не скачивание зависимостей.

--------------------------------------------------------------------------------
13. Работа с CMake и Ninja
--------------------------------------------------------------------------------

PMake может читать CMake-generated `build.ninja` напрямую:

    cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release
    cd build
    pmake

Реализованы основные конструкции Ninja, используемые CMake: rule, build,
default, include/subninja, depfile с deps=gcc и deps=msvc (для MSVC-команды
необходимо включить `/showIncludes`), rspfile, restat, generator,
неявные и order-only входы, phony и pool=console (последовательное выполнение;
консольный ввод/вывод Ninja не воспроизводится).
Известные ограничения:

  - Implicit outputs (секция `|` перед `:`) игнорируются; граф может оказаться неполным.
  - Не поддерживается dyndep (например, динамические зависимости C++20 modules).
  - Если в `default` перечислено несколько целей, по умолчанию выбирается только первая.
  - Пользовательские named pools не поддерживаются.
  - Как и в PMake DSL, команды запускаются напрямую, без shell по умолчанию.
  - Для полного списка сверяйтесь с docs/NINJA_COMPAT.md.

Кэш PMake отдельный от `.ninja_deps` и `.ninja_log`. `compile_commands.json`
PMake не экспортирует; CMake может создать этот файл отдельно с параметром
`-DCMAKE_EXPORT_COMPILE_COMMANDS=ON`.

--------------------------------------------------------------------------------
14. Очистка и диагностика
--------------------------------------------------------------------------------

Показать план без запуска команд:

    pmake -n
    pmake -n app

Посмотреть цели и команды:

    pmake -t targets
    pmake -t commands
    pmake -t commands app

Очистить объявленные выходы:

    pmake -t clean
    pmake -t clean app

`clean` пропускает phony- и generator-цели и защищает типичные исходники и
манифесты. При указании цели очищаются только её выходы, а не выходы её
зависимостей. Если файл не объявлен как выход сборки, clean не обязан его удалять.
При ошибке удаления команда выводит путь и возвращает ненулевой код.

Отладочный вывод:

    pmake -v
    pmake --no-color
    pmake -q

Если сборка не запускает ожидаемую задачу:

  1. Проверьте путь к манифесту через `-f`.
  2. Запустите `pmake -n -v`, чтобы увидеть план и команды.
  3. Убедитесь, что выход существует и объявлен в build.
  4. Проверьте входы, неявные зависимости и depfile.
  5. Если кэш повреждён, удалите `Project-cache.pmake` и повторите сборку.
  6. Проверьте код возврата исходной программы и её stderr.

--------------------------------------------------------------------------------
15. Полный пример C++-проекта
--------------------------------------------------------------------------------

Структура каталога:

    project/
      build.pmake
      src/
        main.cpp

Файл src/main.cpp:

    #include <iostream>

    int main() {
        std::cout << "Hello from PMake\n";
        return 0;
    }

Файл build.pmake:

    pmake_required_version = 1.0

    if os == "windows" {
        cxx = "g++"
        exe_ext = ".exe"
    } else {
        cxx = "g++"
        exe_ext = ""
    }

    cflags = "-std=c++20 -O2"

    rule compile {
        command     = "${cxx} ${cflags} -c ${in} -o ${out} -MMD -MF ${out}.d"
        description = "Компиляция ${in}"
        depfile     = "${out}.d"
        deps        = "gcc"
    }

    rule link {
        command     = "${cxx} ${cflags} ${in} -o ${out}"
        description = "Компоновка ${out}"
    }

    build "build/main.o" : compile "src/main.cpp"
    build "build/hello${exe_ext}" : link "build/main.o"
    alias all : "build/hello${exe_ext}"

Сборка и запуск:

    pmake

    Windows:      build\hello.exe
    Linux/macOS:  ./build/hello

При изменении main.cpp PMake перекомпилирует объектный файл и затем обновит
программу. При изменении только заголовка, перечисленного в depfile, будет
пересобрана соответствующая compile-задача и её зависимые цели.
